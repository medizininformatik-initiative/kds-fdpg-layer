# Style Guide: DE → EN derivation for FDPG labels

> **Status:** Draft v0.3 — 2026-06-02
> **Purpose:** Operational rules for deriving English short descriptions, definitions and profile titles from harmonized German FDPG labels.
> **Companion document:** [datenkatalog-styleguide.md](datenkatalog-styleguide.md) (German labels — primary reference)
> **Target audience of labels:** International clinical researchers without FHIR background.

The German style guide defines *what* gets labeled and in what *form*. This document defines the **derivation procedure** — given a harmonized DE label, how do you produce the EN label?

It is written to be executable by both human reviewers and LLM batch-translation runs. Every rule is unambiguous, every transformation has worked examples, every escape hatch is documented.

### Where labels land

EN labels are stored as FHIR designations (`en-US`) on FDPG profile elements and consumed by:

1. **FDPG application portal** (forschen-fuer-gesundheit.de) — feature selection in international applicant mode.
2. **FDPG Datenkatalog** (IG pages) — EN column in module tables.
3. **Feasibility tool** (cohort selection) — element descriptions in query builder, EN locale.

See the [reference UI mockup in the DE guide](datenkatalog-styleguide.md#referenz-ui-merkmalselektion-im-antragsportal). The same UI is shown in EN locale; profile names, short labels and definitions are swapped 1:1 for their EN equivalents.

---

## 1. Derivation procedure

For each element with a harmonized DE label, follow these steps in order.

**Step 1 — Identify the input.**
Sources, in priority:
- DE `^short` — researcher-facing short label (e.g., "Klinisch relevanter Zeitpunkt")
- DE `^definition` — researcher-facing definition (e.g., "Zeitpunkt der Probenentnahme.")
- DE profile title — column 1 in the Datenkatalog

If no harmonized DE label exists yet, **stop** and author the DE label first per [DE styleguide §3–§4](datenkatalog-styleguide.md). EN cannot lead DE.

**Step 2 — Check the canonical table.**
Look up the element path in `input/data/canonical-labels.json`. If found *and* the meaning matches this profile's use (not profile-specific), use the canonical `en_short` / `en_def` directly. Done.

**Step 3 — Apply translation rules.**
For profile-specific elements or elements not in the canonical table, translate using:
- §3 transformation patterns (mechanical)
- §4 vocabulary table (~120 common DE→EN mappings)
- §5 untranslated terms list (acronyms, proper nouns, DE-only terms)

**Step 4 — Apply form constraints.**
Verify the EN result against §6 form rules (sentence case, noun phrase, length, no end punctuation on short, period on definition, no FHIR jargon).

**Step 5 — Anti-pattern check.**
Verify the EN result doesn't trigger any §7 anti-patterns. If it does, rewrite.

**Step 6 — Write back.**
- Cross-module canonical → add to `input/data/canonical-labels.json`
- Module-specific → add to `scripts/element-labels-<module>.json` (planned per `bd kds-fdpg-layer-bl6`)
- The FSH `Translation(...^short, en-US, ...)` extensions are then auto-generated by `enrich-fsh-translations.py`.

## 2. Decision tree: canonical vs. profile-specific

```
              Does this element appear in ≥3 unrelated profiles
              with the SAME DE label and SAME meaning?
                              │
                  ┌───────────┴───────────┐
                  │ Yes                   │ No
                  ▼                       ▼
            CANONICAL                PROFILE-SPECIFIC
            → canonical-labels.json  → element-labels-<module>.json
            → e.g.: status, subject, → e.g.: Breslow depth, TNM date,
              encounter, identifier,   HLA typing component,
              note, basedOn,           Tumor cell content
              clinicalStatus
```

**When in doubt: lean toward profile-specific.** Canonical entries are deliberately generic; if a label carries any module-specific clinical context, it belongs in a module file. Putting `code` as canonical → "Coding of the content" destroys Labor's "LOINC code for the test ordered".

## 3. Transformation patterns

Mechanical transformations applied to DE input.

### 3.1 FHIR-resource name swap

When a DE label is a German clinical name that corresponds to a FHIR resource type, use the FHIR resource name — not a literal translation.

| DE | EN | Wrong literal |
|---|---|---|
| Behandlungsfall, Fall, Kontakt | Encounter | Treatment case |
| Diagnose | Diagnosis (or Condition in FHIR-tech contexts) | — |
| Probe, Probenmaterial | Specimen | Sample |
| Anforderung | Request (or ServiceRequest) | Demand |
| Befund (Dokument) | Report | Finding |
| Befund (Beobachtung) | Observation | Finding |
| Verabreichung | Administration | Giving |
| Verordnung | Prescription (or MedicationRequest) | Order |
| Einwilligung | Consent | Permission |
| Prozedur, Eingriff | Procedure | Intervention |
| Vorgehen | Procedure | Approach |

### 3.2 Verb form → noun phrase

DE often uses nominalized verbs ("Durchführung", "Verabreichung"). EN short labels are noun phrases too — **never** convert to a verb form.

| DE | EN |
|---|---|
| Durchführung | Performance |
| Verabreichung | Administration |
| Aufzeichnung | Recording |
| Feststellung | Assessment |
| Bewertung | Evaluation |
| Erfassung | Capture |
| Entnahme | Collection |
| Untersuchung | Examination |
| Behandlung | Treatment |
| Anwendung | Use, Application |

**Wrong:** "Indicates the time of administration"
**Right:** "Time of administration"

### 3.3 Reference phrases (idioms)

| DE | EN |
|---|---|
| Verweis auf den/die ... | Reference to the ... |
| Referenz zu ... | Reference to ... |
| Basiert auf ... | Based on ... |
| Teil von ... | Part of ... |
| Abgeleitet von ... | Derived from ... |
| auf die/den sich ... bezieht | that ... relates to |
| in dem ... erfasst wurde | in which ... was recorded |
| an dem ... festgestellt wurde | when ... was established |

### 3.4 Gendering: drop in EN

German uses gender-neutral notation (`*in`, doublings). English doesn't gender singular clinical nouns — use the bare singular noun.

| DE | EN |
|---|---|
| Patient*in | Patient |
| Patientin oder Patient | Patient |
| Anforderer*in | Requester |
| Durchführende*r | Performer |
| Erfassende*r | Recorder |
| Behandelnde*r | Treating clinician |
| Verantwortliche*r | Responsible person |
| Patient*innenidentifikator | Patient identifier |

**Never** produce forced gender constructions: ~~Patient/Patientess~~, ~~Performer/Performress~~.

### 3.5 ValueSet enumerations in definitions

When the DE label inlines ValueSet codes, translate each code to the EN display from the codesystem:

| DE | EN |
|---|---|
| aktiv \| abgeschlossen \| widerrufen \| fehlerhaft eingegeben | active \| completed \| revoked \| entered-in-error |
| unbestätigt \| vorläufig \| bestätigt \| widerlegt | unconfirmed \| provisional \| confirmed \| refuted |
| therapeutisch \| palliativ \| diagnostisch \| präventiv | therapeutic \| palliative \| diagnostic \| preventive |
| Entwurf \| aktiv \| inaktiv | draft \| active \| inactive |

If the codesystem publishes only DE displays (e.g., BfArM, DKG): keep DE codes, add an EN gloss in parentheses on first occurrence:
`aktiv (active) | abgeschlossen (completed)`.

### 3.6 Compound terms

DE compound words often map to multi-word EN phrases:

| DE | EN |
|---|---|
| Behandlungsfall | Encounter |
| Aufzeichnungsdatum | Recorded date |
| Geburtsdatum | Date of birth |
| Erkrankungsbeginn | Onset of disease (or Onset) |
| Probenmaterial | Specimen material |
| Tumorzellgehalt | Tumor cell content |
| Fachabteilungsschlüssel | Department key |
| Versicherungsidentifikator | Insurance identifier |

## 5. Terms that stay in DE or as acronym

### 5.1 Established acronyms (uppercase as-is)

TNM, HPO, ICD-10-GM, ICD-O-3, LOINC, SNOMED CT, NGS, ECOG, WHO, NCT, EudraCT, OPS, ATC, PZN, UNII, CTCAE, KDS, MII, FDPG, IHE, XDS, EDQM, KDL, DKG, DIMDI, BfArM, OncoTree, MONDO, OMIM, HER2, MSI, PD-L1, MMR, RNA, DNA, HRD, ALK, EGFR, BRAF, KRAS, RKI, KBV, GKV, DICOM, FHIR, UICC, AJCC.

### 5.2 Proper nouns (verbatim, with original casing)

OncoTree, Orphanet, MII KDS, ICD-O, RxNorm, BfArM, RKI, WHO, KBV, GKV, DIMDI, DICOM, FHIR, Pathologie-eRegister.

### 5.3 German clinical terms without clean English equivalent

- `Off-Label` — medical convention term, used in EN literature too. Keep verbatim.
- `Fachabteilungsschlüssel` — DKG identifier system, no real EN equivalent. Use `Department key (Fachabteilungsschlüssel)` on first occurrence, then `Department key` thereafter.
- `Pseudonymisiert` → `pseudonymized` (translate — concept exists in EN).
- `Strukturierte Daten`, `Module-Begriffe` (KDS-Modul-Namen) — judge case-by-case. Onkologie module title → "Oncology module" works; `MTB` → keep as MTB (acronym already).

**When in doubt:** prefer the EN clinical term if well-established in international clinical literature (PubMed, Cochrane); keep DE only when no equivalent exists.

## 6. Form rules

### Short label

| Rule | Right | Wrong |
|---|---|---|
| Noun phrase, no verb | Time of collection | Indicates the time of collection |
| Sentence case | Reference to the encounter | Reference To The Encounter |
| 2–6 words | Clinical status | The current clinical status of the diagnosis |
| No end punctuation | Masked insurance identifier | Masked insurance identifier. |
| No FHIR jargon | Reference to encounter | Encounter slice reference |
| No value lists | Status | active \| completed |

### Definition

| Rule | Right | Wrong |
|---|---|---|
| 1–2 sentences, period at end | Reference to prior tumor diseases. | Reference to prior tumor diseases |
| 40–120 chars (max 200) | Encounter in which the laboratory order was placed. | An encounter or episode of care. |
| Researcher context | LOINC code for the laboratory parameter ordered. | A code identifying this concept. |
| Not FHIR-spec verbose | Identifier of the laboratory request. | Identifiers assigned to this order instance by the orderer and/or … |

### Profile title (column 1)

- Sentence case (only first word + proper nouns/acronyms uppercase)
- No FHIR type in parentheses — `Encounter` not `Encounter (Encounter)`
- No MII/FDPG/PR prefix
- Use FHIR-spec resource names when they match clinically
- Drop gendered constructions

**Right examples:** `Patient`, `Diagnosis`, `Laboratory request`, `Oncologic diagnosis primary tumor`, `TNM classification`, `Consent document`, `Breslow depth`.

## 7. Anti-patterns

| Don't | Do | Why |
|---|---|---|
| `Patient/Patientess` | `Patient` | Forced gendering reads poorly |
| `Encounter (Fall)` | `Encounter` | No parenthetical DE in EN label |
| Title Case for profile names | Sentence case | Matches FHIR-spec rendering |
| `Indicates the time of …` | `Time of …` | Short = noun phrase |
| `active \| completed` as short | Short = "Status"; values in definition | Scanability |
| `Treatment case` | `Encounter` | FHIR-name > literal translation |
| `The healthcare event during which …` | `Encounter in which the observation was made.` | FHIR-spec text is not researcher prose |
| Keeping upstream `^short` "Who and/or what the observation is about" | Replace with canonical "Patient" | FHIR base defaults are noise |
| `ICD-10-GM-Code` | `ICD-10-GM` | System label is implied |
| Inconsistent EN for same element across profiles | Use canonical | Consistency > local cleverness |
| `Subjekt` (DE-leak in EN) | `Patient` | Translation, not transcription |
| `Coding of the content` for `code` in Labor profile | Profile-specific: `LOINC code for the test ordered` | Canonical applies only when meaning is generic |

## 8. Worked examples

Each example shows DE input, the procedure steps, and the resulting EN output.

### Example 1 — Cross-module canonical element

**Input:**
- DE `^short` = "Patient*in"
- DE `^definition` = "Patientin oder Patient, auf die sich die Ressource bezieht."
- Element: `subject`

**Step 2 (canonical lookup):** Found. canonical `en_short` = "Patient", `en_def` = "The patient that the resource relates to."

**Output:** `Patient` / `The patient that the resource relates to.`

### Example 2 — Profile-specific clinical concept

**Input:**
- DE `^short` = "Breslow-Tiefe"
- DE `^definition` = "Breslow-Tiefe des Primärtumors in Millimetern."
- Element: `code` in Oncology Breslow profile

**Step 2:** Not in canonical (profile-specific). **Step 3:** "Breslow" stays (proper noun). "Tiefe" → "depth". "Primärtumor" → "primary tumor". "in Millimetern" → "in millimeters".

**Output:** `Breslow depth` / `Breslow depth of the primary tumor in millimeters.`
**Write-back:** Add to `element-labels-onkologie.json`.

### Example 3 — Reference-phrase element

**Input:**
- DE `^short` = "Frühere Tumorerkrankungen"
- DE `^definition` = "Verweis auf frühere Tumorerkrankungen, nach denen die aktuelle Diagnose aufgetreten ist."
- Element: `extension:occurredFollowing` in Oncology

**Step 3:** "Frühere" → "Prior". "Tumorerkrankungen" → "tumor diseases". "Verweis auf … nach denen … aufgetreten ist" → "Reference to … that preceded …".

**Output:** `Prior tumor diseases` / `Reference to prior tumor diseases that preceded the current diagnosis.`

### Example 4 — ValueSet enumeration in definition

**Input:**
- DE `^short` = "Klinischer Status"
- DE `^definition` = "Klinischer Status der Diagnose: aktiv | Rezidiv | inaktiv | Remission."
- Element: `clinicalStatus`

**Step 2 (canonical):** Found for short. **Step 3.5:** translate codes per ValueSet (FHIR clinical-status).

**Output:** `Clinical status` / `Clinical status of the condition: active | recurrence | inactive | remission.`

### Example 5 — Acronym preservation

**Input:**
- DE `^short` = "TNM-Klassifikation"
- DE `^definition` = "TNM-Klassifikation des Primärtumors (UICC 8. Auflage)."

**Step 3:** "TNM" stays. "Klassifikation" → "classification". "Auflage" → "edition". "UICC" stays.

**Output:** `TNM classification` / `TNM classification of the primary tumor (UICC 8th edition).`

### Example 6 — Gendering drop in role label

**Input:**
- DE `^short` = "Anforderer*in"
- DE `^definition` = "Person oder Organisation, die die Anforderung gestellt hat."
- Element: `requester`

**Step 2:** Canonical. `en_short` = "Requester", `en_def` = "Person or organization that made the request."

**Output:** `Requester` / `Person or organization that made the request.`

### Example 7 — Codesystem with only DE display

**Input:**
- DE `^short` = "Fachabteilungsschlüssel"
- DE `^definition` = "Fachabteilungsschlüssel nach DKG (z.B. 0100 = Innere Medizin)."

**Step 5:** "Fachabteilungsschlüssel" → keep DE in parens on first occurrence (§5.3). "Innere Medizin" is in a code value — translate to "Internal Medicine".

**Output:** `Department key (Fachabteilungsschlüssel)` / `DKG department key (e.g. 0100 = Internal Medicine).`

### Example 8 — Replacing FHIR base default

**Input upstream:**
- `^short` = "Who and/or what the observation is about" (FHIR R4 base default)
- No DE Translation
- Element: `subject` in ICU profile

**Step 2:** Canonical exists for `subject`. **Step 7 (anti-pattern §7 row "Keeping upstream …"):** the FHIR base default is noise, replace.

**Output:** Replace `^short` with `Patient`. Add `Translation(^short, de-DE, Patient*in)` and `Translation(^short, en-US, Patient)`.

### Example 9 — Profile-specific with upstream EN that's wrong register

**Input upstream:**
- `^short` = "Subjekt" (DE leak), Translation `en-US` = "Subject" (auto-generated literal)
- Element: `subject` in Lab profile

**Step 4 form check:** "Subject" violates §4.3 vocabulary (subject → Patient in EN clinical context). **Step 5 anti-pattern §7 row "Subjekt (DE-leak in EN)":** override.

**Output:** Override Translation `en-US` → `Patient`. Update DE harmonized → `Patient*in`.

### Example 10 — Module-specific term not yet in vocab

**Input:**
- DE `^short` = "Tumorzellgehalt"
- DE `^definition` = "Anteil der Tumorzellen in der untersuchten Probe in Prozent."
- Element: `value[x]` in Pathology

**Step 3:** "Tumorzellgehalt" not in vocab — derive: "Tumor cell content". "Anteil … in Prozent" → "Percentage of …".

**Step 6 write-back:** Add to `element-labels-patho.json`. Also add `Tumorzellgehalt → Tumor cell content` to §4 vocab for future runs.

**Output:** `Tumor cell content` / `Percentage of tumor cells in the examined specimen.`

## 9. Reviewer checklist

When reviewing a batch of derived EN labels (per module):

- [ ] **a) Canonical coverage:** Did obvious cross-module elements (`status`, `identifier`, `subject`, `encounter`, `code`) use canonical labels?
- [ ] **b) Profile-specific quality:** Are profile-specific labels clinically meaningful (not generic "Coding of the content")?
- [ ] **c) FHIR-base leaks:** Any remaining `^short` texts like "Who and/or what the observation is about" or "Business Identifier for observation"?
- [ ] **d) Form:** Sentence case for titles, noun phrases for shorts, period-ending sentences for definitions?
- [ ] **e) Vocabulary consistency:** subject/Patient consistent? encounter/Treatment-case consistent? No "Reference" mixed with "Verweis"?
- [ ] **f) Acronyms:** TNM, HPO, ICD-* correctly preserved (uppercase, no translations)?
- [ ] **g) Gendering:** Removed `*in` suffix etc., no `Patient/Patientess` constructions?
- [ ] **h) ValueSet enums:** Translated to EN codes where codesystem provides them; DE-with-EN-gloss where it doesn't?
- [ ] **i) Write-back:** New translations added to canonical or module file, so next consumer doesn't re-derive?

## 10. Maintenance

When adding a new element label:

1. Decide canonical vs. profile-specific (§2 decision tree).
2. Edit the appropriate file:
   - Canonical: `input/data/canonical-labels.json` — add `de_short`, `en_short`, `de_def`, `en_def`.
   - Module: `scripts/element-labels-<module>.json` (planned per `bd kds-fdpg-layer-bl6`).
3. Run `python3 scripts/enrich-fsh-translations.py --module=<module>` — re-generates FSH Translation inserts.
4. Run `python3 scripts/generate-datenkatalog.py` — re-renders Markdown + xlsx.
5. Diff-review the affected profiles; verify no FHIR base default leaks through.

For LM-label upstream outliers (English LM concept names from MII KDS that should display in German), edit `LM_LABEL_OVERRIDES` in `scripts/generate-datenkatalog.py` directly — those are tied to upstream LM element IDs, not FHIR element paths.

## 11. LLM-prompt usage

This style guide is designed to be usable as a prompt context for batch DE → EN translation runs. Recommended prompt template:

```text
You are translating FDPG FHIR element labels from German to English.

Follow these rules strictly:
[paste §3 Transformations, §4 Vocabulary, §5 Untranslated terms,
 §6 Form rules, §7 Anti-patterns]

For each input record (DE short, DE definition, element path, module),
produce:
- en_short: ...
- en_def: ...
- rationale: one-line note on which rule applied, if non-obvious
- review_flag: optional "REVIEW: <reason>" if uncertain

Input batch:
[CSV or JSON records]
```

Critical: **include §7 Anti-patterns in every prompt** — LLMs default to verbose FHIR-spec-style English without that constraint.

Recommended batch size: 30–50 records per prompt. Larger batches drift in vocabulary consistency; smaller batches waste context window.

After the LLM produces output, run the §9 reviewer checklist before write-back. Spot-check 10 % of records manually for clinical accuracy.
